# ระบบนิเทศนักศึกษาฝึกสอน (Student Teaching Supervision System)

คณะครุศาสตร์อุตสาหกรรม — เริ่มต้นที่ภาควิชาครุศาสตร์ไฟฟ้า (ออกแบบเผื่อขยายไปภาควิชาอื่น)

เอกสารนี้เป็น **โครงสร้าง/สถาปัตยกรรมระบบ** สำหรับใช้เป็นพิมพ์เขียวก่อนพัฒนา

---

## 1. ภาพรวมระบบ (Overview)

ระบบบริหารจัดการกระบวนการฝึกประสบการณ์วิชาชีพครู ตั้งแต่ **ก่อนออกฝึกสอน → ระหว่างฝึกสอน → รวบรวมส่งคุรุสภา** เพื่อให้นักศึกษาได้สิทธิขอใบอนุญาตประกอบวิชาชีพครู

เป้าหมายหลัก:
- ลดงานเอกสารกระดาษ ทำให้ทุกฝ่ายเห็นสถานะเดียวกัน (single source of truth)
- ควบคุม "ประตูด่าน" (gate) แต่ละขั้น ไม่ให้ข้ามขั้นตอนที่ยังไม่ผ่านการตรวจ
- เก็บหลักฐานครบถ้วนตามเกณฑ์คุรุสภาเพื่อ export ส่งได้ทันที

---

## 2. ผู้ใช้และบทบาท (Roles & Permissions)

| บทบาท | ขอบเขตหน้าที่หลัก |
|-------|------------------|
| **Admin** | ตั้งค่าระบบ, จัดการปีการศึกษา/รอบฝึก, จัดการผู้ใช้และสิทธิ์, กำหนดเกณฑ์/แบบฟอร์ม, จัดการภาควิชา |
| **เจ้าหน้าที่ (Staff)** | ตรวจสอบเอกสารก่อนฝึก, จัดสรรนักศึกษา–อาจารย์นิเทศ–สถานศึกษา, รวบรวมเอกสารส่งคุรุสภา, ออกรายงาน |
| **อาจารย์นิเทศ (Supervisor)** | ตรวจแผนการสอน/งานที่นักศึกษาส่ง, บันทึกการนิเทศ (ลงพื้นที่), ประเมินผล |
| **นักศึกษา (Student)** | เก็บกิจกรรม/หลักฐานก่อนฝึก, ส่งแผนการสอน/บันทึกระหว่างฝึก, ดูสถานะและผลประเมิน |
| **ครูพี่เลี้ยง (Mentor)** *(optional เฟสหลัง)* | ครูในสถานศึกษาที่ร่วมประเมิน (เข้าผ่านลิงก์เฉพาะ ไม่ต้องมีบัญชีเต็ม) |

**หลักการสิทธิ์:** ใช้ RBAC (Role-Based Access Control) + ขอบเขตข้อมูล (data scope)
- อาจารย์นิเทศเห็นเฉพาะนักศึกษาที่ตนรับผิดชอบ
- เจ้าหน้าที่เห็นเฉพาะภาควิชาของตน (Admin เห็นทุกภาค)
- แยกสิทธิ์เป็น permission ย่อย (เช่น `document.verify`, `evaluation.grade`) เพื่อปรับได้ยืดหยุ่นเมื่อขยายภาค

## 3. Workflow / สถานะของนักศึกษา (State Machine)

หัวใจของระบบคือ **สถานะการฝึกของนักศึกษาแต่ละคนในแต่ละรอบ** เดินหน้าได้เมื่อ "ผ่าน gate" เท่านั้น

```
[ก่อนฝึก]                    [ระหว่างฝึก]                   [หลังฝึก]
COLLECTING ──▶ SUBMITTED ──▶ STAFF_VERIFYING ──▶ ADVISOR_APPROVING
   (เก็บกิจกรรม) (ส่งรวมเล่ม)  (จนท.ตรวจ)          (อาจารย์อนุมัติ)
                                                        │
                                                        ▼
                              TEACHING ◀────────── READY_TO_TEACH
                          (กำลังฝึกสอน+รับนิเทศ)     (ผ่านครบ = ออกได้)
                                    │
                                    ▼
                              EVALUATING ──▶ COMPLETED ──▶ SUBMITTED_TO_KURUSAPA
                              (ประเมินผล)    (ผ่านการฝึก)    (ส่งคุรุสภาแล้ว)
```

เหตุการณ์ย้อนกลับที่ต้องรองรับ:
- `RETURNED` — จนท./อาจารย์ตีกลับให้แก้เอกสาร (มีเหตุผล + ประวัติ)
- `FAILED` / `EXTENDED` — ไม่ผ่าน / ต้องฝึกเพิ่ม

> ทุกการเปลี่ยนสถานะบันทึกลง **audit log** (ใคร–เมื่อไหร่–จากอะไรเป็นอะไร–หมายเหตุ)

## 4. โมดูลหลัก (Modules)

### M1. ระบบผู้ใช้และสิทธิ์ (Auth & Identity)
- Login (แนะนำเชื่อม SSO/บัญชีมหาวิทยาลัย เช่น Google Workspace `@…kmutnb.ac.th` หรือ LDAP)
- จัดการบทบาท, ปีการศึกษา, ภาควิชา, รอบฝึก (cohort/term)

### M2. ก่อนฝึก — เก็บกิจกรรม & ตรวจเอกสาร (Pre-Practicum)
- **บันทึกกิจกรรม/สมุดกิจกรรม** ที่นักศึกษาต้องทำครบก่อนฝึก (checklist กำหนดโดย Admin)
- **อัปโหลดหลักฐาน** (ไฟล์/รูป/PDF) ต่อกิจกรรม
- **รวมเอกสาร (Document Bundle)** — ระบบประกอบเป็นชุดเดียวให้ตรวจ
- **Verify workflow 2 ชั้น:** เจ้าหน้าที่ตรวจ → อาจารย์อนุมัติ (ผ่าน/ตีกลับพร้อมคอมเมนต์)

### M3. จัดสรรและจับคู่ (Placement)
- สถานศึกษา (โรงเรียน/สถานประกอบการ) — ทะเบียนสถานศึกษา
- จับคู่ นักศึกษา ↔ อาจารย์นิเทศ ↔ สถานศึกษา ↔ ครูพี่เลี้ยง

### M4. ระหว่างฝึก — แผนการสอน & นิเทศ (Supervision)
- นักศึกษาส่ง **แผนการสอน/บันทึกหลังสอน/ชิ้นงาน** เป็นรายสัปดาห์หรือรายคาบ
- อาจารย์นิเทศตรวจ/ให้ความเห็นในแต่ละชิ้น
- **บันทึกการลงพื้นที่นิเทศ (Visit Log):** วันที่, ครั้งที่, สถานที่, ภาพถ่าย/หลักฐาน, ข้อสังเกต (กำหนดจำนวนครั้งขั้นต่ำได้)

### M5. ประเมินผล (Evaluation)
- **แบบประเมินยืดหยุ่น (Form Builder):** Admin สร้างแบบประเมิน + เกณฑ์ (rubric) + น้ำหนักคะแนน
- ผู้ประเมินหลายฝ่าย: อาจารย์นิเทศ / ครูพี่เลี้ยง / ประเมินตนเอง
- คำนวณคะแนนรวม + สรุปผลผ่าน/ไม่ผ่าน

### M6. รวบรวมส่งคุรุสภา (Compliance / Export)
- ตรวจความครบถ้วนตามเกณฑ์คุรุสภา (completeness check)
- **Export** ชุดเอกสาร/รายงานตามรูปแบบที่ต้องส่ง (PDF/Excel)
- ติดตามสถานะการยื่นขอใบประกอบวิชาชีพ

### M7. แจ้งเตือน & แดชบอร์ด (Notification & Dashboard)
- แจ้งเตือน (in-app / email / LINE Notify) เมื่อมีของให้ตรวจ, ถูกตีกลับ, ครบกำหนด
- แดชบอร์ดตามบทบาท (จนท.เห็นภาพรวมความคืบหน้าทั้งรอบ, อาจารย์เห็นนักศึกษาในความดูแล ฯลฯ)

## 5. Domain Model (ER แบบย่อ)

```
Department ──┬─< AcademicTerm (ปีการศึกษา/รอบฝึก)
             │
User ──< UserRole >── Role ──< RolePermission >── Permission
User (student) ──1─< Enrollment (นศ. 1 คน ต่อ 1 รอบ)  ← หัวใจของ state machine
                       │  status, current_stage
                       ├─< ActivityRecord ──< Attachment      (M2 เก็บกิจกรรม)
                       ├─< DocumentBundle ──< VerificationStep (M2 ตรวจเอกสาร)
                       ├─1 Placement ── School, Supervisor, Mentor   (M3)
                       ├─< LessonPlan / WorkItem ──< Comment   (M4 แผนการสอน)
                       ├─< SupervisionVisit ──< Attachment     (M4 ลงพื้นที่)
                       ├─< Evaluation ──< EvaluationScore      (M5)
                       └─< AuditLog                            (ทุกการเปลี่ยนแปลง)

FormTemplate ──< FormField        (แบบฟอร์ม/เกณฑ์ที่ Admin กำหนด — M2/M5)
School (สถานศึกษา), Supervisor(=User), Mentor
```

**ตารางที่ทำให้ขยายภาควิชาได้:** ทุก entity สำคัญผูก `department_id` และเกณฑ์/แบบฟอร์ม/checklist เป็น **data ที่ตั้งค่าได้ (configurable)** ไม่ hardcode → เปิดภาคใหม่ = สร้าง Department + กำหนดแบบฟอร์มของภาคนั้น โดยไม่ต้องแก้โค้ด

---

## 6. การเผื่อขยายหลายภาควิชา (Multi-Department)

1. **Data-driven config** — checklist กิจกรรม, ขั้นตอน verify, แบบประเมิน เป็นข้อมูลในฐานข้อมูล กำหนดต่อภาคได้
2. **Data scoping** — ทุก query กรองด้วย `department_id` โดยอัตโนมัติ (middleware)
3. **Workflow ร่วม** — state machine เดียวกันทุกภาค แต่ "เนื้อหาแต่ละ gate" ต่างกันได้
4. เริ่ม deploy จริงเฉพาะ **ครุศาสตร์ไฟฟ้า** ก่อน แล้วเปิดภาคอื่นเมื่อพร้อม (feature flag ต่อภาค)

## 7. ข้อเสนอ Tech Stack

> ปรับได้ตามความถนัดทีม — ด้านล่างคือค่าเริ่มต้นที่เหมาะกับงานนี้

| ส่วน | เสนอ | เหตุผล |
|------|------|--------|
| Frontend | **Next.js (React) + TypeScript + Tailwind** | รองรับภาษาไทย, responsive, พัฒนาเร็ว |
| Backend | **Next.js API routes / NestJS** หรือ **Laravel (PHP)** | เลือกตามความถนัดทีม |
| Database | **PostgreSQL** | เหมาะกับ relational + audit log |
| ORM | Prisma / Eloquent | |
| Auth | NextAuth / SSO มหาวิทยาลัย | ล็อกอินด้วยบัญชี `@…kmutnb.ac.th` |
| File storage | เก็บบน NAS/Synology หรือ S3-compatible (MinIO) | มีไฟล์หลักฐานเยอะ |
| Deploy | Docker บน Synology NAS หรือเซิร์ฟเวอร์คณะ | สอดคล้องกับ path SynologyDrive ปัจจุบัน |

## 9. แผนพัฒนา (Roadmap แนะนำ)

- **Phase 0** — วางฐาน: Auth, ปีการศึกษา/รอบ, จัดการผู้ใช้+ภาควิชา, state machine
- **Phase 1** — ก่อนฝึก: เก็บกิจกรรม + รวมเอกสาร + verify 2 ชั้น (M2)
- **Phase 2** — จัดสรร + ระหว่างฝึก: แผนการสอน + บันทึกนิเทศ (M3, M4)
- **Phase 3** — ประเมินผล + form builder (M5)
- **Phase 4** — รวบรวมส่งคุรุสภา + export + แดชบอร์ด/แจ้งเตือน (M6, M7)
- **Phase 5** — เปิดภาควิชาอื่น + ครูพี่เลี้ยงร่วมประเมิน
